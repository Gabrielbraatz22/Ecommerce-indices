O Problema

⚠️ Consultas sem otimização

Sem índices, o banco percorre todas as linhas da tabela para responder a uma busca — o chamado Sequential Scan.

📉 Impacto no negócio

  • +1 s de carregamento → −7% de conversão (Google)
  • +1 s de carregamento → +11% de abandono (Akamai)
  • Estoque incorreto → pedidos cancelados

Por que o e-commerce é crítico?

Uma loja de médio porte com 5.000 pedidos/dia gera mais de 7 milhões de registros por ano entre pedidos, itens e movimentações. Sem tuning, as consultas ficam progressivamente mais lentas.

O Que Acontece Sem Índice?

🐢 Sequential Scan (sem índice)

O banco lê todas as linhas da tabela, uma por uma, para encontrar o que precisa.


Em 6 milhões de movimentações, isso pode demorar minutos.


Custo: O(n) — dobra o volume, dobra o tempo

→

🚀 Index Scan (com índice)

Com um índice B-tree, o banco vai diretamente ao dado, como um índice de livro.


Em 6 milhões de registros, encontra em milissegundos.


Custo: O(log n) — 100× mais dados = apenas ~7 passos extras

Diagnóstico com EXPLAIN ANALYZE: mostra o plano real de execução, tempo em ms, páginas lidas do disco vs cache e o tipo de scan escolhido pelo otimizador

Como o Tempo Cresce com o Volume

📈 Sem índice — crescimento linear

Dobra o volume de dados → dobra (ou mais) o tempo. Em 1M pedidos a C6 chega a 110 segundos.

📉 Com índice — crescimento logarítmico

100× mais dados = apenas ~7 comparações extras no B-tree. O tempo cresce de forma quase plana.

Escala logarítmica · linhas sólidas = sem índice · tracejadas = com índice

Verde escuro ≥ 95% · verde ≥ 85% · laranja ≥ 70% · vermelho < 70%

❌ Plano SEM índice

Seq Scan on movimentacoes_estoque Filter: (produto_id = 500) Rows Removed: 5.999.900 Actual Rows: 100 Execution Time: 62.000 ms -- Leu 6M linhas para retornar 100

✅ Plano COM índice composto

Index Scan Backward on idx_movimentacoes_produto_data Index Cond: produto_id = 500 Actual Rows: 100 Execution Time: 12 ms -- Leu exatamente 100 linhas -- ORDER BY eliminado pelo índice

💡 Por que o índice composto (produto_id, data DESC) é tão eficiente?

Ele atende ao filtro WHERE produto_id = 500 E ao ORDER BY data DESC em um único acesso — sem Sort adicional. O resultado é um Index Scan Backward que lê apenas as páginas necessárias.

Lendo o EXPLAIN ANALYZE

EXPLAIN (ANALYZE, BUFFERS) SELECT ... FROM movimentacoes_estoque WHERE produto_id = 500 ORDER BY data_movimentacao DESC LIMIT 100; -- SAÍDA: Index Scan Backward on idx_movimentacoes_produto_data cost=0.43..8.56 rows=100 actual time=0.08..11.4 Buffers: shared hit=112 read=0 Planning Time: 0.4 ms Execution Time: 12.1 ms

🚨 Sinal de alerta no plano: "Rows Removed by Filter"

Se o EXPLAIN mostra que foram removidas 5.999.900 linhas para retornar 100, o banco fez um trabalho desnecessário de 60.000× o necessário. Um índice nessa coluna de filtro resolve imediatamente.

💡 Por que índices compostos superam índices simples?

O índice (categoria_id, ativo, estoque_atual) atende à Consulta 1 inteira com um único acesso ao índice. Com três índices separados, o PostgreSQL faria um Bitmap AND — três acessos, depois uma combinação. Um índice composto certo elimina esse custo extra.

Tipos de Índice no PostgreSQL

🌲 B-tree — padrão

Suporta =, <, >, BETWEEN, ORDER BY. Ideal para status, datas e FKs. Custo O(log n) para qualquer operação.

#️⃣ Hash

Somente igualdade (=). Mais rápido que B-tree em lookups exatos por SKU ou CPF quando só igualdade é necessária.

🔍 GIN

Para JSONB e busca de texto. Essencial quando produtos têm atributos variáveis por categoria (cor, voltagem, tamanho…).

📦 BRIN

Índice compacto: armazena só o mín/máx de cada bloco. Perfeito para movimentacoes_estoque.data — tabelas gigantes com inserção sequencial por data.

🎯 Index-Only Scan — o mais eficiente de todos

Quando todas as colunas necessárias estão no índice (via cláusula INCLUDE), o PostgreSQL nem toca nas páginas de dados. Zero I/O de heap — lê apenas o índice.

Além dos Índices

🗂️ Particionamento

Divide movimentacoes_estoque por mês ou ano. Consultas temporais leem só a partição relevante — o restante nem é aberto (partition pruning).

📊 Materialized Views

O ranking de produtos (C5) é pré-calculado e armazenado. Consulta passa de segundos para milissegundos. Atualizado com REFRESH MATERIALIZED VIEW.

🧮 Configuração de Memória

  • shared_buffers = 25–40% da RAM
  • work_mem = 64 MB — sort em memória
  • effective_cache_size = 75% da RAM

🔬 pg_stat_statements

Extensão que monitora as queries mais lentas em produção. Fornece dados reais para decisões de tuning baseadas em evidências — não em suposições.

Boas Práticas de Escrita SQL

❌ Evitar

-- Função na coluna quebra o índice WHERE DATE(data_pedido) = '2024-01-01' -- Traz colunas desnecessárias SELECT * FROM produtos -- OFFSET alto é O(n) LIMIT 20 OFFSET 10000

✅ Preferir

-- Range preserva o índice WHERE data_pedido >= '2024-01-01' AND data_pedido < '2024-01-02' -- Colunas específicas SELECT id, nome, preco FROM produtos -- Keyset pagination: O(log n) WHERE id > :last_id LIMIT 20

⚠️ VACUUM e ANALYZE

O otimizador baseia suas decisões em estatísticas de distribuição dos dados. Tabelas com muitos UPDATEs acumulam "dead tuples" que degradam o desempenho. Rodar ANALYZE após cargas de dados garante que o otimizador escolha o plano correto.
